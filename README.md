# MachineLog

**把一台电脑的状态，写成 AI 智能体读得懂的仓库。**

你有没有过这种经历：让 AI 帮你改电脑配置，它不知道你之前做过什么，把已经修好的东西又改坏；或者你换了个新会话，得从头解释「我这台机器装了什么、哪些不能动」。

MachineLog 就是解决这个的：**用 git 仓库记录本机的每一次改动，让下一个接手的智能体（或三个月后的你自己）快速知道现状、避开雷区。**

---

## 它解决什么

| 没有 MachineLog | 有 MachineLog |
|---|---|
| 每个新会话都要重新解释环境 | 智能体读 `STATE.md` 就知道现状 |
| 改动没有记录，出问题查不到原因 | 每次改动都有「为什么、影响什么、怎么回滚」 |
| 不知道哪些操作是禁区 | 红线写在最显眼的地方 |
| 多个智能体互相踩脚 | 每次提交带标识，知道是谁改的 |

## 核心设计（三分钟看懂）

### 五个文件，各回答一个问题

| 文件 | 回答什么 | 体量 |
|---|---|---|
| **`STATE.md`** | **这台机器现在是什么样** | ~70 行，**脚本生成** |
| **`LESSONS.md`** | **踩过的坑和可复用的判断** | 按需查 |
| `OUTLINE.md` | 某类东西**为什么**是现在这样 | 按主题分节 |
| `log/YYYY-MM-DD.md` | **某天**具体做了什么 | 按天分文件 |
| `README.md` | 规则、红线、机器概况 | 一次读完 |

**关键原则：按需读，不要全读。** `STATE.md` 永远先读，其余按任务决定。

### 三层结构：事实 / 结论 / 过程

```
STATE.md     事实层  现在是什么样         脚本生成，随时准确
LESSONS.md   结论层  以后该怎么做         人工沉淀，故意写得慢
OUTLINE.md   结论层  某类东西为什么这样
log/         过程层  某天具体做了什么      只追加，不改
```

**为什么要分 `LESSONS.md` 和 `OUTLINE.md`**：

- `OUTLINE.md` 回答「**这类东西**现在什么状态」——按主题组织，状态变了就覆盖
- `LESSONS.md` 回答「**遇到这个情况**该怎么办」——按场景组织，永不过期，带置信度

遇到报错时，你会去翻 `OUTLINE.md` 吗？大多数人不会，直接就开始排查了。所以**可复用的判断必须单独抽出来**，放在一个"遇到问题就来查"的位置。

### 双索引：主题 + 时间

```
想知道「为什么显示器老是掉分辨率」
  → 读 OUTLINE.md §显示  ← 主题索引，给出结论

想知道「上个星期三改了什么」
  → 读 log/2026-11-19.md  ← 时间索引，给出过程
```

两者不重复：**OUTLINE 存结论，log 存过程。**

### 红线摆在最前面

机器上有些操作是**不可逆或代价极高**的（删数据目录、重置系统、动磁盘分区）。这些写在 `STATE.md` 和 `README.md` 开头，不用翻到文档深处。

## 快速开始

### 1. 建仓库

```bash
mkdir ~/MachineLog && cd ~/MachineLog
git init
cp -r /path/to/machine-log/templates/* .
cp -r /path/to/machine-log/tools .
cp -r /path/to/machine-log/.githooks .
cp /path/to/machine-log/STATE.example.md STATE.md
git config core.hooksPath .githooks
git add -A && git commit -m "初始化本机记录 [Agent: 你的智能体标识]"
```

### 2. 填 `STATE.md`

按你的机器实际情况改。**这个文件后续由脚本生成**，手工改只在初始化时。

### 3. 开始记录

每次改动完，在 `log/今天日期.md` 追加一条：

```markdown
## 14:30  一句话标题

- **智能体**：平台-模型-对话id
- **操作**：具体做了什么（命令 / 注册表路径 / 文件路径）
- **原因**：为什么要做，解决什么问题
- **影响**：改变了什么状态，哪些东西会受影响
- **回滚**：怎么撤销（能回滚的必须写）
```

---

## 为什么是「五个字段」

`操作 / 原因 / 影响 / 回滚` 这个结构不是随便定的，它对应四个问题：

| 字段 | 三个月后你会问 |
|---|---|
| **操作** | 我到底改了什么？ |
| **原因** | 当时为什么要改？ |
| **影响** | 改完之后什么东西变了？ |
| **回滚** | 想撤销的话怎么撤？ |

**「原因」最重要**——没有它，记录就只是操作日志，无法判断这个改动现在还要不要保留。

**「回滚」是保险**——写不出回滚方法的改动，往往意味着风险很高，应该重新考虑要不要做。

## 强制机制（钩子）

两个 git 钩子把规则变成硬约束：

| 钩子 | 检查 | 逃生通道 |
|---|---|---|
| `pre-commit` | 必须改 `log/` 下的文件 | `git commit --no-verify` |
| `commit-msg` | 提交信息必须带 `[Agent: ...]` | 同上 |

**为什么要钩子**：规则写在文档里，智能体可能忘。钩子让「不记录就提交不了」。

**为什么留逃生通道**：只改错别字这种，不值得写一条 log。

## 智能体标识

多人（或多个 AI）协作时，得知道谁改的。格式：

```
平台-模型-对话id
```

例：`Claude-Code-sonnet-4.5-a1b2c3d4`、`Cursor-gpt-5-e5f6g7h8`

`tools/agent-id.sh` 会从常见环境变量自动识别：

```bash
./tools/agent-id.sh <模型名>
# → Claude-Code-sonnet-4.5-a1b2c3d4
```

## 目录结构

```
.
├── README.md              # 本文件：规则 + 红线 + 机器概况
├── STATE.md               # 状态快照（脚本生成）
├── OUTLINE.md             # 主题索引（为什么这样）
├── log/
│   └── YYYY-MM-DD.md      # 时间索引（做了什么）
├── tools/
│   ├── agent-id.sh        # 生成智能体标识
│   └── gen-state.sh       # 生成 STATE.md
├── .githooks/
│   ├── pre-commit
│   └── commit-msg
└── templates/             # 空白模板（复制到你的仓库）
```

## 适合谁

**适合**：
- 用 AI 智能体（Claude Code / Cursor / Copilot / 自建 agent）管理本机环境的人
- 一台机器上装了很多工具链、配置复杂、踩过坑的人
- 想给「不可逆操作」加一道记录保险的人

**不适合**：
- 只用一个软件、没什么配置的人（成本大于收益）
- 需要实时监控/自动采集的场景（这是人工+钩子的方案，不是监控系统）

## 设计取舍

| 我们选了 | 而不是 | 为什么 |
|---|---|---|
| **Markdown 文件** | 数据库 / JSON | 智能体直接读，人也能读，不用解析 |
| **git 仓库** | 云笔记 / wiki | 有历史、能 diff、能回滚、离线可用 |
| **手工 + 钩子强制** | 全自动采集 | 自动采集会淹没重点；人写的「原因」才有价值 |
| **主题 + 时间双索引** | 单一线性日志 | 查「为什么」和查「哪天」是两种不同需求 |
| **红线独立成节** | 混在规则里 | 危险操作要一眼看到 |

## 真实使用示例

这个框架来自一个真实场景：**一台装了几十个工具链的 Windows 笔记本，长期用 AI 协助维护。**

半年下来积累的经验（已脱敏，见 `examples/`）：

- 「显示器偶尔掉分辨率」的根因是 **EDID 降级**，不是驱动问题
- 「删了文件空间没释放」是因为某些工具把文件放进**回收站中转目录**
- 「DSH 崩溃」的根因是配置文件被写入了 **UTF-8 BOM**

这些坑的共同点：**现象和根因隔得很远**。不记下来，下次还会踩。
