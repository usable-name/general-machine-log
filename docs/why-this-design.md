# 为什么这样设计

这个框架不是凭空想的，是从**实际踩过几十个坑之后**收敛出来的。这份文档解释每个设计决定背后的取舍，方便你按自己的情况改。

---

## 1. 为什么不用数据库 / 云笔记

**核心约束：智能体要能直接读。**

| 方案 | 问题 |
|---|---|
| 数据库 | 智能体要写查询代码，多一层出错机会 |
| JSON/YAML | 人能读但难写，长文本全是转义符 |
| 云笔记（Notion 等） | 要 API key、要联网、可能限流 |
| **Markdown 文件** | 智能体用 `read` 就能读，人用编辑器就能改 |

**另一个好处：git 本身就是版本控制。** 每条记录都有时间戳、作者、diff，不用自己实现历史。

---

## 2. 为什么分「主题 + 时间」两个索引

因为查询需求本来就分两种：

```
「显示器为什么会掉分辨率？」     → 我要的是结论和原因
「上周三改了什么？」             → 我要的是过程和顺序
```

**一个线性日志无法同时满足两者。** 你会遇到这些情况：

- 只按时间记：想知道「显示这块现在什么状态」，得翻几十天日志
- 只按主题记：想知道「某个改动是哪次做的」，查不到

**双索引的分工**：

| | OUTLINE.md | log/ |
|---|---|---|
| 存什么 | **结论**（现在是什么样、为什么） | **过程**（那天具体做了什么） |
| 读法 | 查某一节 | 查某一天 |
| 更新时机 | 状态改变时**覆盖**旧内容 | 只**追加**，不改旧的 |

**注意最后一行**：OUTLINE 是「当前快照」，log 是「不可变历史」。这个区别很重要——OUTLINE 里不会有「改回了」这种记录，因为它只反映现状。

---

## 3. 为什么 log 要五个字段

四个字段对应四个三个月后你会问的问题：

| 字段 | 三个月后的追问 | 不写的后果 |
|---|---|---|
| 操作 | 我到底改了什么？ | 无法复现 |
| 原因 | 当时为什么要改？ | 不知道还需不需要 |
| 影响 | 什么东西变了？ | 出问题找不到关联 |
| 回滚 | 怎么撤销？ | 只能硬扛 |

**「原因」是最容易被省略、也最重要的一个。**

很多记录只写「修改了 X 配置」，但三个月后你根本不知道当初为什么要改。没有原因，就无法判断这个改动现在是不是还合理。

**「回滚」是个风险探测器。**

如果一条改动写不出回滚方法，通常意味着：它不可逆、或者影响面不清。**这本身就是「要不要做」的信号。**

> 实践中有一条硬规则：**写不出回滚字段的改动，先别做，把风险想清楚再说。**

---

## 4. 为什么用钩子强制

规则写在文档里，智能体可能忘——这不是智能体的问题，是设计问题。

**「不记录就提交不了」比「请记得记录」有效得多。**

代价是偶尔会挡掉合理操作（比如只改了个错别字），所以留了 `--no-verify` 逃生通道。

**关键是逃生通道要显式**：让人知道自己在绕过规则，而不是悄悄放过。

---

## 5. 为什么智能体标识要包含平台和模型

```
平台-模型-对话id
例：Claude-sonnet-4.5-a1b2c3d4
```

**为什么不是「User」或「AI」**：

- 同一台机器上可能有多个智能体在动（不同 IDE 的、不同会话的）
- 出问题时要知道「这条记录是哪个模型写的」——不同模型的理解能力、犯错模式不同
- 对话 id 能让你回溯到那次会话的完整上下文

**实际案例**：某次排查中发现，同一天有 WorkBuddy 和 DSH 两个智能体都在改配置。没有标识根本分不清谁改的。

---

## 6. 为什么红线单独成节

**危险信息必须在最显眼的位置。**

如果红线混在「给智能体的规则」里，智能体可能读完前 5 条规则就开始干活，根本没看到第 12 条写着「不要删 D:\Files」。

**红线的判断标准**（来自实践）：

> **删掉这条红线后，智能体还能安全行动吗？能，那它就不是红线，只是建议。**

按这个标准，一般机器的红线只有 2-5 条。写太多等于没写。

**红线要写「为什么 + 后果」**：

| 差 | 好 |
|---|---|
| 注意数据安全 | 不要删 `D:\Files`——7 个符号链接指向它，删了微信记录和 IDE 配置全没 |
| 小心操作 | 不要重置系统——会破坏上述链接，软件全部重置成初始状态 |

---

## 7. 为什么 STATE.md 由脚本生成

**状态会变，文档不会自动跟着变。**

`STATE.md` 里的磁盘余量、工具版本、插件清单，全是「今天准确、下周就过时」的信息。

**人工维护的后果**：要么忘记更新（信息过期），要么频繁更新（浪费时间）。

**脚本生成的好处**：
- 每次想更新就重跑，10 秒搞定
- 不会忘（因为数据是现采的）
- 格式一致

**代价**：手工加的备注会被覆盖。所以备注应该写在 `OUTLINE.md` 里，那是人工维护的。

---

## 8. 为什么不用「全自动采集」

有工具能做全自动记录（监控文件系统、抓进程、记命令历史）。**没采用，原因：**

1. **噪音太大**：自动记录会产生大量无意义条目（打开了个文件、跑了个查询），把重要的埋掉
2. **缺少「原因」**：机器只能记录「做了什么」，无法记录「为什么」——而原因是最有价值的部分
3. **需要人工判断**：什么算「一次改动」，需要人（或智能体）来判断

**当前方案是折中**：数据（STATE.md）自动采集，判断（log 条目）人工写。

---

## 9. 什么情况下这套框架不适用

**不适合**：

- **只用一个软件、没什么配置** —— 记录成本大于收益
- **需要实时监控/告警** —— 这是人工方案，不是监控系统
- **多人共用一台机器且互相不知道** —— 需要先有协作约定，否则记录会打架
- **需要不可否认的审计** —— git 可以随便改历史，不满足合规审计要求

**适合**：

- 一个人（或人和 AI 协作）维护一台配置复杂的机器
- 改动有一定风险，需要留后路
- 长期使用，需要跨会话的知识积累

---

## 10. 演进建议

如果你用下来觉得有用，可以考虑这些增强（本框架没内置）：

| 增强 | 什么时候需要 |
|---|---|
| `gen-state.sh` 加更多探测项 | 想让它更全面 |
| log 按月归档 | 单文件超过 500 行时 |
| 加 `TROUBLESHOOT.md` | 排查经验多到 OUTLINE 放不下 |
| 接入 CI 自动校验格式 | 多人协作时 |
| 给 log 加 machine-readable frontmatter | 想自动生成统计时 |

**但别一开始就做这些。** 先用最简版本跑两周，看哪里真的痛，再加。
